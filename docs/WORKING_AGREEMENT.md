# Working Agreement

## How we work
1. Start with the business outcome and user problem, not a technology choice.
2. Break work from macro to micro to nano only where it helps a decision or execution.
3. Label statements as facts, hypotheses, proposals, or decisions.
4. Use issues for discrete research questions and deliverables once the project workflow is established.
5. Keep decisions in `docs/DECISIONS.md` and evidence in `docs/VALIDATION_LOG.md`.
6. Prefer small, reviewable changes and meaningful commit messages.
7. Do not implement features before the relevant validation gate.
8. For each proposed automation, define permissions, outputs, acceptance criteria, failure paths, and escalation.
9. Measure cost and quality per completed outcome, not raw model usage or task count.

## Definition of done: research task
- Answers the question with traceable sources or primary evidence.
- Includes publication dates and limitations.
- Separates observations from interpretations.
- Records implications for the product decision.
- Identifies unresolved questions and next action.

## Definition of done: future workflow
- Produces the specified artifact or external result.
- Meets acceptance criteria.
- Respects access and approval rules.
- Preserves relevant execution history.
- Handles failure or routes it to a person.
- Is evaluated against a measurable success threshold.
